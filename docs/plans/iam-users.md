# IAM users implementation plan

Ship IAM user create and delete, the `GetUser` read, the `ListUsers` name filter, the CLI commands, and the wiki pages together as one feature release after the owner's decisions, the manager's probes, independent review, and a live write check.

## Constraints

- Authorities: [IAM users design](../design/iam-users.md), [IAM users API and checks](../design/iam-users-api.md), [IAM writes](../design/iam-writes.md) for guards and the secret file, [CLI](../design/cli.md), [routing](../../AGENTS.md#ai-agent-definitions-and-routing), [workflow](../../instructions/workflow.md), [testing](../../instructions/testing.md), [security](../../instructions/security.md), [live data](../../instructions/live-data.md), [Go](../../instructions/go.md), [documentation](../../instructions/documentation.md), [release](../../instructions/release.md), and [accepted ADRs](../adr/README.md). Stop on a missing contract or conflicting authority instead of inventing one.
- Gates: no code task starts before the owner answers every [owner decision](../design/iam-users.md#owner-decisions), the design and this plan pass independent review, and Task 2's probes record the create response, the get shape, the list filter, and the delete codes. A document move or approval upgrades no inferred shape.
- The manager owns owner questions, probes, fixtures, briefs, worktrees, verification, live calls, Git, PRs, release notes, signed tags, and publication. Each code task uses `gpt-6.1-sol` medium through implementer. One separate `gpt-6.1-sol` xhigh code-review job reviews the complete release after the last code task, including the adversarial items in the design's threat analysis and security review, then confirms fixes. Failure investigation uses `gpt-6.1-sol` xhigh through troubleshooter. Reviewers never fix reviewed source or review their own work.
- Run tasks in order. Start each worker with `git status --short` in a credential-free owned worktree with the [CLAUDE.md sandbox settings](../../CLAUDE.md#claude-routing-and-invocation). Workers are not alone and preserve others' edits. Workers never change Git state, read `.env`, private example configs, or `examples/basic/output/`, fetch dependencies, or call the live API. At most three workers run across all slices; the manager inspects each diff and reruns required checks before dependent work.
- Keep the SDK standard-library only and public imports stable. `ListUsers` existing callers see no change. `User` keeps its fields; `UserDetail` is new. Reuse `iam.ErrSelfChange`, `iam.ErrPrivilegedChange`, `iam.ErrInUse`, and `iam.ErrCreateUnconfirmed`; add no new CLI error class.
- A password never reaches stdout, stderr, `--debug` output, an error, a capture, a fixture, a test name, a golden file, argv, or a log. Usernames and user IDs are account data: fixtures and tests use `<id>` and `<account>` or short synthetic values.
- Use one line per paragraph or list item, unpadded tables, no dates or em dashes, and at most 450 lines. Do not put plan, task, or review IDs in code, tests, comments, wiki pages, or other living docs. Human docs wrap at 80 columns; generated pages change through their sources.

## Common checks

Each implementation task's Checks includes its behavior tests, `make check` including `go test -race ./...`, `go vet -tags live ./...`, `go vet -tags livewrite ./...`, `go test -tags live -run '^$' ./livetest/`, `go test -tags livewrite -run '^$' ./livetest/`, `bash scripts/check-sdk-deps.sh`, `git diff --check`, and generated-doc freshness. Compile-only live checks make no API calls. Do not fetch dependencies; report unavailable tools or caches to the manager. Never retry a flaky check into a pass.

Generated-doc freshness means generate with `go run ./cmd/vngcloud gen-docs <scratchpad>/generated-wiki` into a private temporary directory and compare every generated page byte-for-byte against `docs/wiki/`. A task that owns a generated page copies only that page, then regenerates and compares all pages. Never run repository-wide `make gen-docs` in a worker. Wiki changes also require `make wiki-preview` and local page-link and anchor inspection.

- Write the failing behavior test before the code. Use `httptest`, a fake API that records every request, injected readers for randomness, temporary directories for files, and synthetic values. Decode fixtures through the SDK, never from decoded SDK output.
- Every password test uses a canary value and inspects stdout, stderr, the debug log, the capture hook, every error in the unwrap chain, and `fmt`, `slog`, and `json.Marshal` of the Input and Output.
