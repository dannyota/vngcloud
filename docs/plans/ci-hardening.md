# CI hardening implementation plan

**Goal:** Make PR-head validation, master landing, Wiki publication, and release eligibility checkable, fix scanner and tool-audit gaps, and apply the owner's approved GitHub controls without weakening existing checks.

**Architecture:** CI supplies one stable `CI required` check for its mandatory jobs. A manager-run evidence checker accounts for every triggered validation workflow on the exact head, including conditional runs. Review-only jobs are optional input, classified by workflow or app purpose. Wiki publishes only a validated current master commit. Repository settings provide a second control while the manager retains the approved admin bypass and responsibility for fast-forward landing and signed releases.

## Review focus

- Trace empty validation evidence, missing validation workflows, wrong repositories, synthetic merge SHAs, changed PR heads, stale master, duplicate runs, rerun attempts, skipped jobs, cancellations, delayed validation runs, and API pagination or transport failures. A green aggregate cannot excuse another triggered validation workflow's failure. Review-only work is optional and cannot block landing.
- Trace PR code, workflow edits, shell inputs, tokens, caches, artifacts, and publishing permissions. Never interpolate PR titles or branch names directly into shell code; pass data through quoted environment variables or structured arguments. Preserve redaction and read-only validation permissions. Do not introduce privileged artifact or cache consumption from PR jobs.
- Confirm that Wiki cannot publish a branch, a stale master, or a commit whose validation failed. Publication must not wait on its own unfinished workflow or a serialized sibling publisher. Separate validation prerequisites from the manager's post-landing gate for all validation runs and state the lack of an atomic transaction across two repositories.
- Confirm that scanner exceptions match the stated false positive only, tool lookup errors fail, all action references are inspected, and current version comments cannot disguise stale SHAs or image digests. Distinguish scanner errors from findings and remotely configured blocking policy.
- Confirm the owner's settings exactly, including the sole required context, bypass scope, declined Semgrep environment, and UI-only Copilot change. No inherited restriction or existing unrelated rule may be overwritten. No settings probe may delete or force-update master or published tags.
- Confirm each task has local regression checks, exact-head green runs, a meaningful red test, finite waits, and truthful completion evidence. Measure cost and duration before claiming improvement; native runtime tests and cross-compilation are different checks.

## Evidence contract

1. Capture PR number, base and source repositories, exact head `H`, current master `M`, and the reviewed workflow identities. Require the intended master target and `H` descended from current `M`. Inspect the full branch log and diff, signatures, and required independent project review. Read any available GitHub reviews and comments, including Copilot's, and fix or answer concrete findings. Do not request reviews to fill an optional slot or wait for a final-head review after fixes.
2. Derive the expected workflow/job set from the reviewed event and path matrix below and the complete change set. Use PR merge-base-to-head paths for PRs and before-to-after paths for pushes, including both sides of renames. A truncated path listing or missing comparison base fails; it does not prove docs-only scope. CI is always required. Each conditional exclusion has recorded paths and a reason. Manual validation requires its selected workflow regardless of path exclusions.
3. Enumerate every workflow run and check run for `H` with complete pagination and appropriate PR/source association, including `pull_request`, `push`, `workflow_dispatch`, and schedule when present. Include check runs without a normal workflow entry. Classify review-only work by the reviewed workflow or app purpose, not an arbitrary display name, and exclude it from required validation evidence. Do not wait for or require review-only runs. A validation run triggered by a review remains required. Match immutable validation workflow and check-run identities. Detect changed or newly introduced workflows from the reviewed diff; do not let a renamed workflow disappear from the expected set. An API error, incomplete listing, unexpected evidence type, or empty CI set fails closed.
4. Treat every independent validation run ID separately. A later successful run of the same workflow does not replace a different failed run. Inspect every attempt from 1 through the current attempt. Require completed `success` for every applicable attempt and retain each rerun reason for diagnosis only. Any prior non-success attempt remains blocking; neither a later pass nor a manager reason string overrides it. Fix the cause on a new head and collect new evidence; reruns cannot launder flaky tests into success. Require completed `success` for each applicable run. Reject failure, cancellation, timeout, neutral, action-required, pending state, or a missing expected run. Older superseded heads are outside `H` but their current-head cancellations are not ignored.
5. Inspect jobs as well as workflow conclusions. Every mandatory job must succeed. Only event/path-inapplicable jobs listed in the matrix may be skipped, such as publishing during a PR; a skipped required job is failure. `CI required` runs even when dependencies fail or skip and accepts only the full expected CI job set with successful results. A skipped or spoofed aggregate is not sufficient evidence.
6. Every validation job that checks source uses `${{ github.event.pull_request.head.sha || github.sha }}`, asserts `git rev-parse HEAD` equals the expected SHA, and records it with the run ID and attempt using the identity transport below. An aggregation-only job checks dependency results and their identity without executing submitted code. Run metadata or a PR association alone does not prove checkout identity. Cache reuse cannot substitute for invoking the required checks on that checkout.
7. Immediately before landing, re-read PR head, master, and the complete validation evidence set. Restart on changed heads, ancestry, or validation run set. Save the accepted SHA, validation run IDs, attempts, URLs, conclusions, expected exclusions, and evidence cutoff privately. External GitHub review findings are optional input and are not required evidence. The required independent project-review record remains separate. The manager alone fast-forwards master; before the automated checker exists, the manager performs and records this same procedure manually.
8. After landing, wait for every applicable master-push run on `H` and, when enabled and triggered, Wiki publication. Tasks 1 and 2 require successful read-only Wiki previews where applicable and explicit evidence that publication is disabled; never count a preview as publication. From Task 3, an expected publisher cannot be absent. Confirm master still names `H`, and record publication's full source SHA when enabled. Serialize manager landings through this gate. A failed post-landing run blocks the next slice and tags; fix forward through a reviewed PR. Tag only the exact eligible commit, verify its source and tag signatures, and preserve one feature per release.
9. Recheck validation evidence before a tag or publication because a later manual validation run can appear after the earlier cutoff. No finite wait proves future validation runs cannot exist. Use bounded polling with an explicit failure on timeout, not a silent exemption. Do not wait for review-only runs. A trusted manager-side checker cannot be replaced with an unreviewed script from the PR under evaluation.

### Identity transport and trust boundary

Task 2 makes the existing tested-source requirement machine-readable through a runner-generated check annotation. Job outputs remain inputs to `CI required`; summaries remain human-readable. Neither is a REST evidence source. The format and adapter below implement the existing requirement without adding write permission, signing credentials, artifact trust, or an exception to the redirect rule. Independent plan review precedes implementation; real-service verification precedes reliance on the transport.

- Emit exactly one `::notice title=vngcloud-source-identity::{JSON}` from each reviewed identity step after the checkout SHA assertion succeeds and before source checks run. The compact UTF-8 JSON object has exactly `version` (integer `2`), `repository` (`dannyota/vngcloud`), `workflow` (the literal workflow file path), `job` (the workflow job key), `matrix` (an object of reviewed string keys and values, empty for current jobs), `tested_sha` (the full 40-character lowercase commit SHA), `run_id` (positive integer), `run_attempt` (positive integer), `workflow_ref` (string), and `workflow_sha` (the full 40-character lowercase workflow commit SHA). Validate the workflow fields under [execution-source binding](#execution-source-binding). Limit the message to 2048 bytes; reject duplicate JSON keys, missing or extra fields, invalid types, and unknown versions. Build the record from fixed workflow values and runner context, pass values as data, and escape workflow-command data. Never accept PR-supplied commands or evidence files.
- For each run, retrieve its attempt metadata and every page of `/repos/dannyota/vngcloud/actions/runs/{run_id}/attempts/{attempt}/jobs`. Bind each job to that run and attempt, the reviewed workflow ID and path, and its expected job name and matrix entry. Validate the job's `check_run_url` as the fixed repository's numeric check-run path, then reconstruct the request path. Require the expected GitHub Actions app identity from the reviewed policy and a matching job/check-run association. Fetch every page of `/repos/dannyota/vngcloud/check-runs/{check_run_id}/annotations`; require exactly one annotation titled `vngcloud-source-identity`, level `notice`, whose version-2 record matches the expected tested source, workflow execution source, job, matrix, run, and attempt. Missing, duplicate, malformed, truncated, or conflicting identity fails. Require the identity step and source job to succeed. Aggregation-only jobs need successful reviewed dependency checks, not a fabricated source checkout record.
- Review the identity step in the actual workflow definition used by the run, including PR merge-ref workflow differences, under [execution-source binding](#execution-source-binding). A check annotation is a workflow assertion, not a cryptographic measurement of test execution. Require the reviewed checkout assertion, required check invocations, and job conclusions as well as matching annotation data. A later source command that emits another matching title causes rejection. Never accept an unrelated app's annotation or a self-reported identity without the job and attempt binding.
- Use a standard-library Python HTTPS read adapter in `scripts/ci-evidence.py`, separate from evaluation. Construct `http.client.HTTPSConnection` for literal `api.github.com` on port 443 with certificate and hostname verification enabled. Issue only `GET` requests to constructed `/repos/dannyota/vngcloud/` endpoint paths. Accept only the expected successful JSON response; reject every 3xx response before any follow-up request, even for the same host. Do not resolve or request `Location`. No redirect, API-host, repository, proxy, Unix-socket, or TLS override is exposed or inherited from CLI configuration or environment. Do not invoke `gh api` for checker evidence reads; settings and other manager-owned GitHub operations retain their existing authority.
- Validate each pagination link against literal HTTPS host `api.github.com`, port 443, the same repository and endpoint, and the expected query fields before constructing the next numbered-page request. Reject userinfo, fragments, foreign hosts or paths, duplicate query fields, incomplete pages, and transport errors; require complete counts where exposed. Bound request time, total wait, pages, bytes, and retries; hitting a bound fails. Transport retries may repeat a failed read only, never a workflow or test. Treat annotations, API text, logs, and artifacts as untrusted data. Do not execute them, print raw request headers or exception bodies, or use redirected log or artifact downloads as a fallback.
- The adapter accepts only an existing runtime `GH_TOKEN`, supplied explicitly to the trusted reviewed checker process; it never discovers or retrieves credentials. Missing or invalid token input fails before a request. Keep the token in process memory, use it only in the Authorization header to the fixed API host, remove it from the environment inherited by child tools, and never write it to arguments, files, diagnostics, reports, or captured output. In Actions, bind the existing job `GITHUB_TOKEN` to `GH_TOKEN` only for the checker step, with the already specified read permissions. This does not create a token, broaden permissions, or authorize a worker to obtain one.
- Proposed manager launch when no runtime token is already supplied: use a reviewed shell wrapper with tracing disabled to capture `gh auth token --hostname github.com` directly into process memory, check its exit status and nonempty single-line output, then pass the value as `GH_TOKEN` only to the trusted checker child. Never run the token command with its stdout exposed to tools, terminals, or logs; never use a candidate checkout's script for the launch. This stored-token handoff remains pending owner approval below. The checker must not silently attempt it.
- The manager proves the notice appears unchanged in the correct job's annotations on a real PR run and a master-push run, with read-only workflow permissions. Check pagination, the Actions app ID, run/job/check associations, and retention across a successful rerun. Use a disposable head for duplicate or malformed notices and deliberate failures. Do not rely on assumed step numbering or a success-only latest-job listing. Missing annotations or unsupported adapter behavior block Task 2 completion; manual evidence remains necessary until the checker has matching real evidence.

GitHub documents the notice command and optional title in [workflow commands](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#setting-a-notice-message). The [check-runs API](https://docs.github.com/en/rest/checks/runs#list-check-run-annotations) returns annotation title, level, and message with pagination and read access. The [workflow-jobs API](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt) exposes attempt-specific jobs and job check-run URLs; [workflow runs](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run-attempt) exposes attempt metadata. These documented pieces do not prove the complete runner-to-annotation transport in this repository; the manager's real-service probe remains required.

GitHub CLI v2.102.0 [constructs its HTTP client](https://github.com/cli/cli/blob/v2.102.0/api/http_client.go) without a redirect callback; its pinned go-gh dependency [passes that unset callback to `http.Client`](https://github.com/cli/go-gh/blob/v2.16.1/pkg/api/http_client.go). The [go-gh option contract](https://github.com/cli/go-gh/blob/v2.16.1/pkg/api/client_options.go) specifies Go's default redirect policy for that case. The CLI's [redirect test](https://github.com/cli/cli/blob/v2.102.0/api/http_client_test.go) follows a cross-host 302 while withholding authentication, and the [API command flags](https://github.com/cli/cli/blob/v2.102.0/pkg/cmd/api/api.go) expose no redirect refusal control. Token suppression does not satisfy the required request refusal. The [token command](https://cli.github.com/manual/gh_auth_token) outputs a stored token, so it cannot be treated as an ordinary metadata read.

Job and step log downloads return a 302 URL that expires after one minute under the [workflow-jobs API](https://docs.github.com/en/rest/actions/workflow-jobs#download-job-logs-for-a-workflow-run). The step-log endpoint describes its step number as zero-based. This plan does not use either endpoint; using step logs would require separate live verification, and redirected downloads would require resolving the security contract first.

### Execution-source binding

Version-2 identity annotations associate each run attempt with its workflow revision within the approved workflow-assertion trust boundary. Existing run, attempt, job, and check metadata establish associations but do not establish the top-level PR merge workflow revision. No current merge ref, current master, workflow display name, or source-content digest alone fills that gap. Real-service verification remains required before reliance.

GitHub documents `github.workflow_ref` and `github.workflow_sha` in its [contexts reference](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#github-context). The [workflow model](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows#workflow-triggers) selects workflow definitions from the event's commit or ref; the [PR event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request) distinguishes the merge commit from the PR head. The [REST schemas](https://github.com/github/rest-api-description/blob/main/descriptions/api.github.com/api.github.com.json) provide no separate top-level `workflow_sha` in run or job responses. Their `referenced-workflow` schema describes workflows reused by the initial caller, not an identity for that caller. Do not reinterpret an empty list or the PR-head `head_sha` as an execution-source binding.

- Set `workflow_ref` and `workflow_sha` directly from `${{ github.workflow_ref }}` and `${{ github.workflow_sha }}` in the reviewed identity step, through quoted environment data. `workflow_sha` is a full 40-character lowercase commit SHA, recorded separately from `tested_sha` and allowed to equal it; `workflow_ref` must identify the fixed repository, the literal reviewed workflow path, and the expected event ref. Apply the identity transport's 2048-byte bound, strict types, duplicate-key rejection, and exactly-one-title rule. Reject version-1 annotations; current refs cannot supply their missing execution-source fields. The private project-review record remains version `1`.
- Bind each version-2 record through the existing run, attempt, job, check, and Actions app checks. All source jobs in an attempt must agree on the workflow source tuple. Each attempt must retain its own records, and repeated attempts of the same top-level workflow must agree on its source tuple. Different independent runs on the same tested head can have different workflow revisions; inspect every revision. Aggregation-only jobs use their run's reviewed definition and required dependency evidence without claiming a source checkout. The current workflows define their jobs directly; unexpected reusable-workflow execution requires its own reviewed source contract and cannot borrow the caller's source identity.
- Retrieve the exact source bytes at the asserted commit through the fixed-host read adapter. Read `/repos/dannyota/vngcloud/git/commits/{workflow_sha}`, traverse nonrecursive `/git/trees/{tree_sha}` responses for the reviewed `.github/workflows/` path, and read `/git/blobs/{blob_sha}`. Construct every endpoint from validated object IDs, never response URLs. Require matching object IDs, complete trees, unique path components, directory tree entries, and a regular-file blob; reject symlinks, submodules, missing objects, invalid base64, and size or transport bounds. Verify the decoded blob's Git object ID and compute its SHA-256 digest. Use no mutable-ref fallback, raw download URL, redirected log, or artifact. GitHub documents these reads in [Git commits](https://docs.github.com/en/rest/git/commits#get-a-commit-object), [Git trees](https://docs.github.com/en/rest/git/trees#get-a-tree), and [Git blobs](https://docs.github.com/en/rest/git/blobs#get-a-blob).
- The trusted reviewed policy binds each allowed source revision to `repository`, `workflow_id`, `workflow` path, `workflow_ref`, `workflow_sha`, `blob_sha`, and `content_sha256`, with a report reference covering those exact bytes. The manager and independent reviewer inspect the checkout assertion, context inputs, identity emitter, required checks, dependencies, permissions, and PR merge-source differences in those bytes. The checker requires an exact tuple and digest match, then records the binding for every run and attempt. The manager retains original PR source bindings after landing and before tagging; current master cannot replace them. An unknown revision needs source review, not a Boolean override. Missing retained source or review evidence fails closed.
- Trust limit: these extra fields are workflow assertions carried by the already approved annotation channel. They identify immutable bytes for review and prevent accidental substitution of a moving ref; they do not independently attest that those bytes executed. A malicious workflow can claim another revision, just as it can claim another checkout. Content hashing and the Actions app association do not remove that limitation. Retain the existing trust in reviewed workflows, the full branch and diff review, and independent project review; the checker reports a workflow-asserted source association backed by exact-byte review, not independent execution attestation. Do not describe the added fields as protection against a deliberately falsifying workflow. Requiring independent execution attestation would need a separate design, not an invented REST field or a source-reviewed Boolean.
- Proof gate: the manager must demonstrate the version-2 fields on a real PR run with a distinct merge workflow revision, a master-push run, and both attempts of a successful full rerun, using read-only workflow permissions. Retain the original source bytes and bindings, then show that a later merge-ref change does not replace them. Inspect the known probe workflow and its context bindings at the recorded source commit, and compare its bytes with the immutable API source read; report the workflow-assertion limit of that proof. Offline cases reject missing version-2 fields, unknown revisions, wrong repository/path/ref, mismatched source digests, conflicting job or attempt claims, unavailable historical source, and replacing old PR evidence with current master. Existing failed-attempt, exact-head, signature, independent-review, pagination, and redirect tests remain required.

Version-2 annotations and exact-byte policy bindings remain within the accepted workflow-assertion boundary. They introduce no token handoff, signer, write permission, publisher, or external review requirement. The existing stored-token choice and real-evidence gates remain unchanged. Older runs without execution-source evidence remain ineligible for the automated binding; do not delete runs, waive attempts, or create an empty head to hide missing evidence. The reviewed identity change is a substantive cause fix for future evidence, and manual landing duties remain in force until the checker is verified.

### Attempts, signatures, and manager review inputs

- Read attempt metadata and job evidence for every integer attempt from 1 through each validation run's current attempt; then re-read the run to detect a new attempt. Missing attempts, unavailable old evidence, partial reruns without a complete required job set, and any prior non-success attempt fail closed. Rerun reasons remain diagnostic data with no acceptance effect. Apply the same rule to independent manual validation runs. No infrastructure, cancellation, or flaky-test exception is approved. A new head needs a reviewed cause fix and its own evidence; deleting failed runs or making an empty commit solely to hide a failure is not a fix.
- The manager supplies the expected owner SSH signer identity through the existing trusted public signing configuration outside the candidate checkout. Let `B` be the reviewed pre-landing master SHA. The checker uses Git's signature verification for every introduced source commit in `B..H` and `H` itself, and requires the verified signer to match that owner identity. Missing objects, an unavailable trust configuration, an unsigned commit, another signer, or verification failure blocks acceptance. Do not import trust from the candidate repository, accept a GitHub verified badge as a substitute, change trust settings, or read private signing keys. Run verification from the manager's trusted checkout with replacement objects disabled; the checker never fetches or changes Git state.
- Release mode requires the exact locally available annotated tag object, verifies the owner's SSH signature on that object, and requires its peeled commit to equal eligible `H`. A lightweight tag, wrong target, missing object, or bad signature fails. Pre-landing and post-landing modes do not require a tag that does not exist yet. The manager creates a signed tag only under the release procedure and runs release mode before pushing that tag; the checker never creates or pushes one.
- The manager supplies a private review record outside the PR checkout and fetched artifacts for required independent project reviews. Version 1 identifies `version`, `repository`, `pr`, `head_sha`, `reviewed_base_sha` (`B`), `policy_sha`, `manager`, and a nonempty `reviews` list. Each review records the independent reviewer, author, exact reviewed SHA, report reference, outcome, findings, and fix-confirmation references; an empty findings list records no findings. Require repository, head, reviewed base, and policy SHA to match expected inputs, reviewer and author to differ, an accepting outcome, and final-head fix confirmation for every blocking finding. Retain `B` after landing; current master must then equal `H`, not `B`. Reject missing, stale, contradictory, or malformed project-review input. Do not accept a bare `reviewed=true` flag or review instructions from PR text.
- The checker validates the project-review record's structure and identity bindings, while the manager verifies reports, reviewer independence, and finding resolution. Report automated evidence and manager-recorded project review separately; do not claim that an unsigned manager record cryptographically proves review. Rechecking runs does not replace that manual duty. GitHub reviews and comments, including Copilot's, are optional input: read available items and fix or answer concrete findings without waiting for or requiring review-only work. Publication mode checks source pre-landing machine evidence and master validation. Do not send the private project-review record or owner signing credentials to Actions.

### Pending choices and evidence gates

- No failure waiver, replacement signer, or credential authority is approved. Keep the strict retry rule, required independent project review, and atomic publication documentation. GitHub reviews and comments remain optional input under the approved admin bypass.
- Owner choice pending: permit the manager to hand the existing stored `github.com` login token to the reviewed checker through the memory-only launch described above, or supply an existing runtime `GH_TOKEN` directly. Recommend the restricted handoff. The API account, repository, and read scope remain unchanged, but exporting a token from CLI custody to another process is not established by approved `gh api` access; [standing Git authority](../../instructions/workflow.md#working-rules) does not approve credential reads. Do not perform that export until the owner approves it. Already authorized runtime token use and the existing Actions job token do not require a new credential or wider permissions.
- Manager evidence remains pending for version-2 notice retrieval, immutable execution-source binding, rerun retention and attempt binding, the HTTPS adapter's redirect rejection and pagination behavior, and the existing public owner signer identity. These are verification prerequisites, not requests to replace the owner key or relax acceptance. Report the exact failed prerequisite if a probe cannot establish it.
- A failed annotation probe requires a revised transport contract and independent review before implementation continues. Any proposal to add cross-host downloads, accept a prior non-success attempt, trust another signer, or automate proof of manager review is a new owner decision and remains unapproved. The current plan authorizes none of those alternatives.
